- [x] **M5.1 demo-mode false alarm (hotfix, TDD)** — done 2026-10-30: dashboard showed "Demo mode — the unify API is offline, start it with `unify ui`" while `unify ui` was running. Root cause: `realRunner` let `Bun.spawn` throw `Executable not found in $PATH: "skillshare"` when the pinned backend was absent, so `SkillshareAdapter.detect()` (and therefore `/api/status`, `/api/doctor`, `unify status`) failed with a 500 instead of reporting `installed: false`; the dashboard caught every failed `/api/status` as "offline". Fix: (1) `realRunner` maps spawn failures to exit 127 + stderr (shell semantics, no throw) — a fresh machine now renders live status with `skillshare not installed` instead of breaking the API; (2) `classifyFailure` (apps/dashboard/src/lib/live-state.ts) splits **API offline** (`ApiError.status === 0`) from **API error** (any HTTP status); the banner shows the real message + `unify doctor` hint for the latter, and both banners note the 30 s auto-retry (no reload). (3) `unify ui --host <iface>` / `$UNIFY_UI_HOST` (default `127.0.0.1`, unchanged) so containers/sandboxes can reach the single dashboard+API port. **130 tests pass** (4 runner + 5 live-state + 121 prior), tsc clean.

- [x] **M6 Windows support (TDD)** — done 2026-10-30: `unify init` on Windows reported `skillshare binary not found` right after a "successful" install. Three causes: (1) the Windows asset is a **.zip whose member is `skillshare.exe`**, but extraction shelled out to `unzip` (absent on stock Windows) and wrote/expected an extensionless `skillshare`; (2) `resolveSkillshareBinary` probed only that name; (3) `buildRegistry` bound the resolved binary path **once**, so even a corrected install was never re-detected (`detect()` kept running the pre-install path). Fixes: `skillshare/archive.ts` = dependency-free in-process zip + tar.gz reader (magic-byte sniffing, stored/deflate, ustar, clear errors listing available members); `skillshareBinName(platform)` + platform-aware `resolveSkillshareBinary`; registry resolves the binary **per call** (a long-running `unify ui` also picks up backends installed later); adapter takes `unifyHome` so `$UNIFY_HOME` is honoured by install/cache/detect; `install(manifest, platform)` verifies with the extracted name; init messages now state `--skip-install` vs "still not detected" and print the expected binary path. Also: agentmemory is launched as `node <pkg>/dist/cli.mjs` on win32 (`agentmemory/command.ts`) because npm's `.bin` shim is a POSIX script there, and `unify memory save/recall` bail cleanly when agentmemory is missing instead of throwing a raw ERROR. CI gained a `windows-unit` job (archive/parse/command/init tests + binary build + `unify.exe version`). **157 tests pass** (152 → +5), tsc clean.
- [x] **M6.1 memory-engine provisioning + fast failure (TDD)** — done 2026-10-30: on Windows `unify init` got past skillshare, then hung **180 s** at "ensuring memory server …" and dumped agentmemory's 60-line "Setup required" box twice (once as the log tail, once as a citty stack trace). Root cause found in `@agentmemory/agentmemory@0.9.31`'s bundle: its installer returns early for `IS_WINDOWS || isZipAsset` ("Auto-install unavailable … isn't tar-compatible"), so the Windows `iii-engine` is never installed and the supervisor can never start. Fixes: (1) `agentmemory/engine.ts` provisions the engine from unify — pinned `iii v0.25.0` asset names + SHA-256 table copied from agentmemory's own `III_RELEASE_SHA256`, download → verify → **in-process extract** (shared `adapters/archive.ts`) → `~/.agentmemory/bin/iii(.exe)` (the path agentmemory reads first) → `--version` check; typed `EngineError` codes (unsupported-platform/no-checksum/download/checksum/extract/verify). (2) Windows pre-provisions (agentmemory cannot); other platforms only retry after a failure **and** only when the binary is genuinely absent, so stubs/custom engines keep working. (3) `ensureRunning` now watches the child (`exited`) and scans the log for fatal engine lines — 180 s → **~1 s**, and a failed child is killed so the CLI can't stall on exit (a stray detached supervisor held Bun's event loop: observed as a 60 s hang). (4) `tailOf` strips ANSI/box drawing; failures print one cause line + ≤5 log lines. (5) `init` treats memory startup as non-fatal (`memoryStartHints`) and continues to the skillshare sync; `unify memory` uses the same path; `/api/memory` returns **503** with a one-line cause instead of a 500 dumping the box. (6) `doctor` names a missing engine explicitly. **183 tests pass** (162 → +21: engine 13, fast-fail/tail 5, hints 2, API 503 1), tsc clean.
- [x] **M6.2 two `unify init` regressions from the Windows reports (TDD)** — done 2026-10-30: (1) **memory fast-fail fired on stale logs** — `fatalEngineLine()` scanned the last 4 KB of an *append-only* log, so the "Could not start iii-engine" box left by the previous run aborted the next start in ~1 s and the error quoted an old log; only bytes appended after this run's spawn now count (`statSync(...).size` recorded pre-spawn, passed to `fatalEngineLine`/`tailOf`), and `tailOf` says "(no output from this run)" instead of showing history. Windows now also **verifies** an existing engine every start (`iii --version`) and reinstalls a stale/corrupt `iii.exe` instead of trusting the file's presence, with provisioning logged (`iii-engine 0.25.0 installed`). (2) **`skillshare init failed: ✗ skillshare is already initialized`** — `ensureState` only looked for `~/.config/skillshare/config.yaml`, but skillshare's global config is `%APPDATA%\skillshare\config.yaml` on Windows; it re-ran `init`, got exit 1 and threw, which citty rendered as a stack trace **twice** and killed the rest of init. Now `skillshareConfigPaths()` probes APPDATA/XDG, "already initialized" is treated as success, other failures reduce to one line, and init wraps `ensureState` in `attemptInstall` (which now returns the call's value) so init finishes and syncs. **192 tests pass** (183 → +9), tsc clean; verified end-to-end with the compiled binary (stale-log start no longer aborts; `init` against an already-initialized skillshare completes and applies the sync).
- [x] **M6.3 diagnose agentmemory's engine rejection (TDD)** — done 2026-10-30: on the third Windows run `iii-engine present (0.25.0)` was followed by `agentmemory exited before it was ready (exit 1)` with the dependency's own "Setup required" box. Reading `@agentmemory/agentmemory@0.9.31` + `iii-hq/iii@v0.25.0` sources showed the real check: `iiiBinVersion()` = `execFileSync(bin,["--version"],{stdio:["ignore","pipe","ignore"],timeout:3000})`, i.e. **stdout only, hard 3 s, non-zero exit throws**; when it returns null agentmemory treats the engine as missing and falls into `runIiiInstaller()`, which is a no-op on Windows → "Could not start iii-engine". unify's own probe has no timeout and reads stdout *or* stderr, so it can say "present (0.25.0)" about a binary agentmemory rejects. Fixes: (1) `probeEngineAsAgentmemory()` reproduces that exact check (spawn, kill on timeout, never block on a dying tree) and unify logs the verdict before starting on Windows — `iii-engine seen by agentmemory (v0.25.0, 118ms)` or `warning: agentmemory's engine check failed: <timeout|stderr-only|exit N>`, surfaced as the cause line when the start then fails; (2) the supervisor now runs with `AGENTMEMORY_VERBOSE=1` (log file only, `UNIFY_MEMORY_VERBOSE=0` to disable) so `iii binary:` / `fallback iii at … reports version:` always land in the log; (3) `engineTrace()` lifts those discovery lines out of this run's log and `memoryStartHints()` prints them as "agentmemory's engine check" — hints no longer claim "unify normally installs iii-engine" when the engine *is* installed. **200 tests pass** (193 → +7), tsc clean.
- [x] **M6.4 surface agentmemory's Compose log (TDD)** — done 2026-10-30: fourth Windows run got further than any before — `iii-engine seen by agentmemory (v0.25.0, 58ms)` — and failed one layer down: `error[PROJECT_DID_NOT_START]: …worker-compose.yaml did not start / Compose exited with code 1`. Reading `iii-compose@v0.25.0` showed `ProjectDidNotStart` is raised when the `up` operation status is `Failed` (`lib.rs:829`), i.e. a *container's* error, and that agentmemory only ever prints that summary — the container's own message lives in its Compose daemon log (`<dataDir>/compose/compose-daemon.log`, `%APPDATA%\agentmemory\compose\…` on Windows), which unify never read. Fixes: (1) `agentmemoryDataDir()`/`agentmemoryComposeLog()`/`agentmemoryComposeFile()` mirror the package's `resolveDataDir()` (%APPDATA% / Application Support / XDG_DATA_HOME / `--instance N`); (2) on a Compose-related failure unify reads that log, strips box drawing/progress noise and appends `compose log (…)` with the container's real error — the first guess at `<dataDir>/compose/compose-daemon.log` turned out **not to exist on the real machine**, so `findComposeLog()` now resolves the path from agentmemory's own `engine-state.json` (`logFile`, normally `%USERPROFILE%\\.agentmemory\\compose-<restPort>.log`), then falls back to `~/.agentmemory/compose-<port>.log` and the project dir; (3) `composeFix()` turns the daemon's text into the action — registry/download failures point at **`api.workers.iii.dev`** (the `state`/`http` worker packages), container spawn failures point at docs/SETUP; (4) `memoryStartHints()` splits the message into engine-check / compose / log-tail sections, so a Compose failure no longer claims "agentmemory will not use iii-engine". **209 tests pass** (200 → +9), tsc clean.
